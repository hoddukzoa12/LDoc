# LDoc AI 하네스 설계

다음에 무슨 일을 할지는 코드가 정하고, 모델은 한 번에 한 가지 일만 받습니다. 모델은 값을 쓰지 않고 고르거나 가리키기만 하며, 값은 Rust 코어가 읽고 계산합니다. 타입과 시그니처는 [harness-sketch.ts](harness-sketch.ts)에 있습니다. 전체 구조는 [architecture.md](architecture.md)를 봅니다.

## 1. 설계를 정하는 다섯 가지

1. **턴은 코드가 정합니다.** 화면이 어디에 있고 사용자가 무엇을 했는지로 다음 턴의 종류가 정해집니다(`plan()`). 모델은 "다음에 뭘 할까"를 판단하지 않습니다. 턴 종류마다 지시문, 도구, 스텝 수가 표 하나(`TURN_SPECS`)에 고정됩니다.
2. **모델은 값을 쓰지 않고 가리킵니다.** 모델의 출력에는 금액, 날짜, 이름을 적는 칸이 없습니다. 선택지를 고르거나, 받은 글의 어느 부분인지 가리킵니다. 가리킨 부분을 코어의 해석기가 읽지 못하면 값이 되지 않습니다. 시효 칸에 기억으로 3을 채운 사고는 "쓰지 말라"는 지시가 아니라 "쓸 칸이 없음"으로 막습니다.
3. **턴 하나는 요청 하나이고, 하네스는 기억이 없습니다.** 이 경로는 `store: false`이고 `previous_response_id`를 쓸 수 없어서, 스텝마다 입력 전체를 다시 보냅니다. 그래서 비용은 스텝 수와 쌓인 대화 길이에 비례합니다. 대화를 쌓지 않고 앱의 상태(문서, 빈 필드 목록)에서 매 턴 입력을 새로 만듭니다. 다섯 턴 중 셋은 모델 요청이 한 번입니다.
4. **Rust가 개인정보 구역이고, 기기 밖으로 나가는 문도 Rust 하나입니다.** Mastra가 도는 프로세스에는 이미 가려지고 사용자가 승인한 글만 들어갑니다. 그 프로세스는 네트워크에 직접 닿지 않고 토큰도 갖지 않습니다. 나가는 요청은 전부 Rust가 검사하고 기록한 뒤 보냅니다.
5. **구조화된 결과는 전부 함수 도구의 인자로 받습니다.** 이 경로에서 `text.format`이 되는지는 문서에 없습니다. 함수 도구는 된다고 적혀 있습니다.

## 2. 단위 업무와 형태

형태는 지금의 가설입니다. 8장의 측정으로 확정하거나 바꿉니다. 계산만은 측정 결과와 무관하게 코드에 둡니다(약속 1).

| 단위 업무 | 형태 | 이유 |
| --- | --- | --- |
| 문서 추천 | 모델 턴, 요청 1회 | 문서 150개 제목(7,590바이트)과 추천 기준(3,175바이트)은 지시문에 다 들어갑니다. 찾기 도구를 두면 왕복이 한 번 늘 뿐입니다. |
| 가이드 읽기 | 모델 없는 코드 | 어느 문서의 몇 단계인지는 코드가 압니다. 필요한 절만 지시문에 끼웁니다. 도구(`guide_section`)는 설명 턴에서만 줍니다. 질문이 어느 절에 걸리는지 모델만 알기 때문입니다. |
| 다음 질문 정하기, 묻기 | 모델 없는 코드 | 코어의 `Form`에 라벨, 도움말, 표시 조건이 이미 있습니다. 양식이 곧 문답입니다. 모델 요청 0회. |
| 붙여 넣은 글에서 답 뽑기 | 모델 턴, 요청 1회, 가리키기 | 표기가 제각각인 글에서 어느 말이 어느 필드인지 찾는 일은 모델이 잘합니다. 값 읽기는 코어가 합니다. |
| 답 검사 | 모델 없는 코드 | 코어 `Reader`와 둘째 해석 단계. |
| 인지대, 송달료, 이율, 기산일, 한글 금액 | 모델 없는 코드 | 약속 1. 가이드 37개의 산식 71줄은 전부 사칙연산입니다. |
| 수치 표가 낡았는지 확인 | 명령줄, 모델 없이 MCP 직접 호출 | 볼 조문이 정해져 있습니다. 조문 본문의 해시가 바뀌면 사람에게 알립니다. 관리자가 자기 키로 돌립니다. 송달료 단가는 이 도구로 볼 수 없어 수동 확인 목록에 남습니다. |
| 법령을 찾아 답하기 | 모델 턴, 여러 스텝, 하네스 도구가 korean-law-mcp를 감쌈 | 검색어를 고르고 결과를 읽는 일은 모델 몫입니다. 감싸는 이유는 4장에 있습니다. |
| 서술 문단 쓰기 | 모델 턴, 요청 1회, 코어가 검사 | 모델은 `{{ balance }}` 같은 자리 이름만 씁니다. 코어 `check_prose`와 `render`가 받습니다. |
| 보내기 전 가리기 | 모델 없는 코드 + 사용자 승인 | 6장. |
| 체크리스트, 작성 후 안내 | 모델 없는 코드 | 코어의 `notices`. 가이드 원문은 발췌로 보여 주고 숫자에 "확인되지 않은 수치" 표시를 붙입니다. |
| 평가 실행, 가이드를 양식과 템플릿으로 바꾸기 | 명령줄 | 사용자는 개발자가 아니므로 앱 안에는 명령줄 형태가 없습니다. 명령줄은 관리자와 CI의 것입니다. |

## 3. 프로세스와 경계

```
화면 (React, 웹뷰)        Rust 셸 + ldoc-core                    하네스 프로세스 (Bun 실행 파일 + Mastra)
턴 결정 plan()      ⇄    가리기, 값 읽기, 글 검사          ⇄    TURN_SPECS, 도구, 요청 모양 고치기
후보와 승인 화면   Tauri  로그인, 토큰(키체인), 출처 장부  stdio   네트워크 없음, 토큰 없음
                   명령   나가는 문: 검사, 기록, 전송     JSON-RPC
                              │
                              ├ HTTPS → api.openai.com
                              └ HTTPS → mcp.gomdori.app/law
```

- **하네스 프로세스**는 Mastra 에이전트를 담은 별도 실행 파일입니다. Rust 셸이 AI를 처음 쓸 때 자식 프로세스로 띄우고 앱이 끝날 때 닫습니다. 측정한 시작 시간은 0.4초 안팎, 크기는 116MB입니다(Linux, macOS와 Windows는 미확인).
- **통신은 표준 입출력 위의 JSON-RPC 2.0**이고 한 줄에 메시지 하나입니다. 양방향입니다. Rust가 `runTurn`을 시키고(`HarnessPort`), 하네스가 도는 중에 Rust에게 전송, 출처 등록, 진행 알림을 요청합니다(`CorePort`). 포트를 열지 않습니다.
- **나가는 문은 Rust 하나입니다.** 하네스의 HTTP는 전부 `CorePort.netFetch`로 Rust에 넘어갑니다. 하네스는 주소를 고르지 못하고 정해진 목적지 이름(`openai.responses`, `openai.models`, `law.mcp`)만 댑니다. Rust가 토큰이나 법령 키를 붙이고, 본문을 검사하고(6장), 기록한 뒤 보냅니다. 응답은 조각 단위 알림으로 돌려줍니다.
- **화면은 하네스와 직접 말하지 않습니다.** 화면이 원문을 하네스에 직접 넘길 길이 없어야 가리기를 건너뛸 수 없습니다. `assist_run`은 승인된 `text_id`만 받습니다.
- **코어는 한 벌입니다.** 코어를 WASM으로 하네스에 넣지 않습니다. 하네스는 코어가 필요하면 Rust에 묻습니다.
- **하네스는 턴 사이에 상태가 없습니다.** `TurnRequest` 하나가 들어가고 `TurnResult` 하나가 나옵니다. 죽으면 다시 띄우면 됩니다. 같은 요청을 평가에서 그대로 다시 돌릴 수 있습니다.
- **평가에서는** 코어를 감싼 작은 실행 파일이 Rust 셸 자리에 앉아 같은 `CorePort`를 말합니다. 앱을 띄우지 않고 턴을 돌립니다.

Mastra를 쓰는 방식은 좁습니다. 에이전트 하나, 턴마다 `agent.stream()` 한 번입니다. `tools`를 요청 맥락의 함수로 두어 그 턴의 도구만 요청에 정의되게 하고, 호출마다 `instructions`, `toolChoice`, `maxSteps`를 `TURN_SPECS`에서 넣습니다. 여러 스텝 턴의 마지막 스텝은 `prepareStep`으로 종료 도구를 강제합니다. Mastra의 메모리, 워크플로, 하위 에이전트, 평가 기능은 쓰지 않습니다.

모델 연결은 AI SDK의 `createOpenAI`에 `fetch`를 끼워 만듭니다. Mastra의 모델 문자열이나 `{ id, url }` 객체는 쓰지 않습니다. 그 둘은 `/v1/chat/completions`로 요청을 보냅니다(11장). 끼운 `fetch`는 두 가지를 합니다. 요청 모양을 이 경로의 규칙에 맞게 고칩니다(`shapeRequest`). 그리고 고친 요청을 `netFetch`로 Rust에 넘깁니다. `shapeRequest`가 하는 일은 넷입니다. `store: false`와 `stream: true`를 박습니다. 이 경로가 받지 않는 필드를 지웁니다. `system` 역할 입력이 있으면 `developer`로 바꿉니다. 실계정에서 필요하다고 확인되면 함수 도구를 네임스페이스로 묶습니다. Mastra나 AI SDK가 판을 올려 요청 모양을 바꿔도 이 경로의 규칙은 여기와 Rust의 문에서 지켜집니다.

로그인은 Rust가 합니다. 시스템 브라우저를 열고 `127.0.0.1` 콜백으로 PKCE를 마친 뒤 토큰을 OS 키체인에 둡니다. 접근 토큰은 1시간이므로 Rust가 요청 직전에 만료를 보고 갱신합니다. 권한에 `chatgpt.tokens.use.direct`가 없으면 로그인만 된 상태로 두고 AI를 켜지 않습니다. 클라이언트 등록 절차는 OpenAI 문서와 T3 Code의 구현(`CodexChatGptAuth.ts`)을 따릅니다. 첫 조각의 배선 확인에서는 OpenAI 키트 `@siwc/local`을 스크립트에서 써도 됩니다.

## 4. 도구

전부 하네스 프로세스 안에서 도는 Mastra `createTool`입니다. 모델이 보는 도구는 일곱 개이고, 한 턴에 많아야 세 개입니다.

| 이름 | 입력 | 출력 | 도는 곳 |
| --- | --- | --- | --- |
| `propose_documents` | 문서 id(카탈로그 열거형) 최대 3개와 이유, 되물을 질문 하나 | 없음. 턴 종료 | 하네스. 검사는 Rust |
| `propose_answers` | `{ field, pointer }` 목록. `pointer`는 선택지, 인용(받은 글의 부분 문자열), 가린 자리 이름 중 하나 | 없음. 턴 종료 | 하네스. 값 읽기는 Rust `resolve` |
| `submit_prose` | 구역 이름, 자리 이름이 든 글 | 없음. 턴 종료 | 하네스. 검사는 Rust `check_prose` |
| `answer` | 글, 출처 이름 목록, 가이드 발췌 위치 목록 | 없음. 턴 종료 | 하네스. 검사는 Rust |
| `guide_section` | 가이드 id, 절(여섯 개 중 하나), 단계 번호 | 그 절의 원문 | 하네스. 앱에 든 가이드 파일을 읽음 |
| `law_search` | 검색어, 법령인지 판례인지 | 성공이면 출처 이름과 결과 목록, 실패면 사유 | 하네스 → korean-law-mcp `search_law`, `search_decisions` |
| `law_article` | 결과의 참조, 조문 | 성공이면 출처 이름과 본문, 실패면 사유 | 하네스 → korean-law-mcp `get_law_text`, `get_decision_text` |

- **종료 도구 넷**은 실행 결과가 없습니다. 인자가 곧 그 턴의 결과이고, Rust가 검사한 뒤에야 화면에 갑니다.
- **가이드 150개를 도구로 넣는 방법**은 `guide_section` 하나입니다. 가이드는 절 제목이 같습니다(150개 모두 용도, 작성 전 확인, 출력 템플릿, 작성 후 안내가 있고 체크리스트는 149개에 있습니다). 그래서 절 단위로 자르는 것은 코드로 믿을 수 있습니다. 단계 안의 질문과 분기 표기는 가이드마다 달라서(굵은 `질문` 표기로 시작하는 가이드는 76개뿐) 그보다 잘게는 자르지 않습니다.
- **korean-law-mcp의 도구 10개를 그대로 주지 않고 둘로 감쌉니다.** 이유는 넷입니다. 요청마다 도구 정의 10개를 보내지 않습니다. `execute_tool`과 `discover_tools`처럼 무엇이든 부를 수 있는 도구를 뺍니다. 검색어가 공개 서버를 지나므로 보내기 전에 코드가 검색어를 검사합니다(가린 자리 이름이나 번호 모양이 있으면 거부). 성공한 결과에만 출처 이름(`S1`)을 발급합니다. 연결은 `@mastra/mcp`의 `MCPClient`에 `url`과 사용자 정의 `fetch`를 주어 Rust의 문을 지나게 합니다. 법령 키는 Rust가 붙입니다.
- **출처 이름이 인용을 묶습니다.** `answer.sources`에는 발급된 이름만 쓸 수 있습니다. 화면의 조문 이름과 본문은 모델의 글이 아니라 Rust에 저장된 조회 결과에서 그립니다. 성공한 조회가 하나도 없으면 모델의 글을 버리고 코드가 "법령을 확인하지 못했습니다"와 사유를 보여 줍니다.

## 5. 턴 제어

다음 턴은 `plan(state, event)`가 정합니다. 부작용이 없는 함수라 단위 테스트로 검증합니다. 사용자가 어느 화면에서 무엇을 했는지가 턴 종류를 정하므로, 의도를 가려내는 모델 호출이 없습니다.

| 턴 | 시작 조건 | 지시문에 넣는 것 | 도구와 선택 | 스텝 | 받아들이는 규칙 |
| --- | --- | --- | --- | --- | --- |
| `recommend` | 문서 선택 화면에서 상황을 적음 | 추천 기준, 카탈로그 150줄(지원 수준 포함) | `propose_documents` 강제 | 1 | id가 카탈로그에 있음. 이유 글이 검사를 통과 |
| `fill` | 양식 화면에서 글을 붙여 넣음 | 지금 보이는 빈 필드의 id, 라벨, 종류, 선택지. 개인정보 필드는 라벨만 | `propose_answers` 강제 | 1 | 필드가 제시된 것임. 인용이 받은 글에 있음. 코어가 값을 읽음 |
| `explain` | 필드나 초안에 대해 물음 | 그 단계의 가이드 절, 필드 정보 | `guide_section`, `answer`. 마지막 스텝은 `answer` 강제 | 최대 3 | 글 검사 통과. 발췌 위치가 실제로 있음 |
| `compose` | 서술 구역에서 "써 주세요" | 자리 목록(이름, 종류, 설명. 값 없음), 사실의 모양(어느 자리가 있고 없는지, 날짜의 앞뒤, 금액의 대소. 값 없음), 가이드 템플릿의 그 구역 | `submit_prose` 강제 | 1 | `check_prose` 통과. 자리가 전부 알려진 이름 |
| `research` | 법령 질문 | 조회 절차, 출처 이름 쓰는 법 | `law_search`, `law_article`, `answer`. 마지막 스텝은 `answer` 강제 | 최대 5 | 출처가 전부 발급된 이름. 글 검사 통과 |

턴마다 같은 규칙입니다.

- **고지는 화면이 합니다.** "법률 자문이 아니다"는 고지는 스킬이 추천할 때와 문서를 낼 때 두 번 보이라고 정합니다. 모델에게 쓰게 하지 않고 화면 코드가 그 두 자리에 고정해 보여 줍니다.
- **도구는 항상 강제입니다.** 모델이 도구 없이 글로 답하는 경로가 없습니다. 종료 도구를 부르지 않고 끝나면 실패입니다.
- **글 검사는 하나입니다.** 모델이 쓴 글은 문서에 들어가든 대화창에 뜨든 `check_prose`를 지납니다. 자리 밖의 숫자, 한글 수사, 조문 번호, 제어 구문이 있으면 버립니다. 법정 수치는 출처 카드의 원문에만 나옵니다.
- **고쳐 다시 시키기는 한 번입니다.** 검사에 걸리면 문제의 종류와 위치만 붙여 같은 턴을 한 번 더 돌립니다. 또 걸리면 버리고 양식으로 돌아갑니다. 양식은 AI 없이 언제나 됩니다.
- **모델이 뽑은 답은 후보입니다.** 양식의 필드 옆에 인용과 함께 뜨고, 사용자가 확정해야 답이 됩니다. 다음에 물을 것은 양식의 다음 빈 필드이고 코드가 그 필드로 옮깁니다.
- **성공은 `response.completed`를 받은 뒤입니다.** 사용 한도 오류(`subscription_sharing_usage_limit_exceeded`, 429)는 스트림 중간에도 옵니다. 그러면 도우미를 멈추고 ChatGPT 설정의 사용량 화면을 안내합니다. 재설정 시각은 추측하지 않습니다. 503은 간격을 늘려 두 번까지 다시 시도합니다. 400 `subscription_sharing_unsupported_capability`는 같은 본문으로 다시 보내지 않고 기록합니다. `refresh_token_expired`와 `invalid_grant`는 다시 로그인입니다.

가리키기가 막지 못하는 것이 하나 있습니다. 맞는 금액을 틀린 필드에 붙이는 일입니다(총액과 받은 금액을 바꿈). 필드 옆의 인용 표시, 사용자의 확정, 코어의 필드 간 검사(받은 금액이 총액 이상이면 거부)가 줄이지만 없애지는 못합니다. 그래서 8장에서 "틀린 값이 받아들여진 수"를 누락과 따로 셉니다.

## 6. 기기 밖으로 나가는 것

AI가 꺼져 있으면(기본) 아무것도 나가지 않고 하네스 프로세스도 뜨지 않습니다.

| 어디로 | 무엇이 | 언제 |
| --- | --- | --- |
| OpenAI 로그인 | OAuth 요청 | 사용자가 로그인을 누를 때 |
| `api.openai.com/v1/models` | 접근 토큰 | 로그인 직후, 계정을 바꿀 때 |
| `api.openai.com/v1/responses` | 우리 지시문, 가이드 발췌, 필드의 라벨과 선택지, 자리 이름, 사용자가 승인한 가린 글, 법령 조회 결과 | 모델 턴마다 |
| `mcp.gomdori.app/law` | 모델이 쓴 검색어(코드 검사 뒤), 조문 참조, 사용자의 법제처 키 | `research` 턴에서만. 처음 켤 때 "검색어가 이 서버를 지납니다"를 알림 |

나가지 않는 것은 다음과 같습니다. `Sensitivity`가 `pii`인 필드의 값(이름, 번호, 주소, 연락처), 편집기의 본문, 가리기 전의 원문, 가린 자리와 원문의 대응표.

가리는 순서는 이렇습니다.

1. Rust `mask`가 세 가지로 가립니다. 양식에 이미 있는 값(공백과 `(주)` 같은 표기 차이를 흡수), 번호류 정규식(주민등록번호, 사업자번호, 전화, 계좌, 차량 번호), 사용자가 화면에서 누른 낱말입니다. 양식 값에서 온 것은 `{{ debtor.name }}`처럼 자리 이름으로 바꾸고, 나머지는 `⟦인물1⟧`로 바꿉니다.
2. 화면이 가린 글을 보여 주고, 사용자가 승인한 글만 나갑니다. 문서 추천처럼 양식이 비어 있을 때는 사전이 없으므로 이름을 가리는 것은 사용자의 눈입니다. 이것은 남는 위험이고 화면에 그렇게 적습니다.
3. Rust의 문이 나가는 본문을 한 번 더 훑습니다(`egress_check`). 번호류 정규식, 이 사건의 개인정보 필드 값(표기 차이 흡수), 승인 기록에 없는 사용자 글 중 하나라도 걸리면 보내지 않고 화면에 무엇이 걸렸는지 보여 줍니다. 1번이 틀려도 3번이 막습니다.
4. 보낸 본문은 Rust가 직접 기록하고 "보낸 내용 보기"에서 그대로 볼 수 있습니다. 하네스가 스스로 보고하는 기록이 아닙니다.

1.1GB 개체명 모델은 넣지 않습니다. 평가에서 실제 누출이 6건 있었고 앱에 싣는 방법도 정해지지 않았습니다.

## 7. 코어가 다루지 않는 149개 문서

하네스에 별도 경로를 두지 않습니다. 지원 수준은 코어 카탈로그의 속성(`Coverage`)이고, 턴은 그 값만 봅니다.

| 수준 | 사용자가 얻는 것 | 만드는 방법 | 지금 |
| --- | --- | --- | --- |
| `computed` | 양식, 계산, 출처 붙은 수치 | Rust 문서 모듈 | 1개 |
| `compiled` | 양식과 템플릿. 계산 없음. 검토 전 표시 | 관리자가 명령줄로 가이드를 묶음으로 바꾸고 사람이 검토 | 0개 |
| `blank` | 가이드의 출력 템플릿을 빈칸 서식으로 엶 | 코드만. 템플릿 절을 `Document`로 읽음 | 149개 |

- **`blank`는 모델 없이 지금 됩니다.** 가이드의 출력 템플릿을 편집기에 그대로 열고 `[성명]` 같은 빈칸을 강조합니다. 템플릿에 박힌 숫자는 전부 "가이드 원문 수치, 확인 필요"로 표시합니다. 가이드의 송달료 5,500원처럼 낡은 값이 실제로 있었기 때문입니다. 작성 후 안내는 안내 문구로 보여 줍니다. 모델이 쓴 값이 없으므로 약속 1을 어기지 않습니다.
- **모델이 가이드를 보고 문서 전체를 쓰게 하지는 않습니다.** 그렇게 하면 모델이 금액과 기한을 쓰게 되고, "검토받지 않음" 표시는 약속 1의 예외가 아닙니다. `recommend`와 `explain`은 149개 문서에도 그대로 됩니다.
- **`compiled`**: 명령줄 `compile-guide doc-NNN`이 가이드의 세 절(정보 수집 단계, 체크리스트, 출력 템플릿)에서 양식과 템플릿 초안을 만듭니다. 빈칸을 뽑는 일은 정규식이 먼저 하고, 모델은 이름과 종류와 표시 조건만 정합니다. 코어가 초안을 검사하고 사람이 검토해 저장소에 넣습니다. 사용자의 요금제를 쓰지 않습니다. 가이드가 계산이나 기한을 요구하는 자리는 채우지 않고 `[확인 필요]`로 남기며 가이드의 규칙을 옆에 보여 줍니다.
- **올리는 순서**: 지급명령 9종 중 독촉절차 신청서 6종(doc-025, 028, 051, 067, 107, 116)은 인지대와 송달료 계산을 이미 있는 코드와 같이 쓰므로 바로 `computed`로 만듭니다. doc-051(임금)은 연 20% 이율 특칙이 따로 필요합니다. 양육비 직접지급명령 2종(doc-054, 088)은 가정법원 절차이고 비용 구조가 달라 여기에 넣지 않습니다. 그 밖의 문서는 `recommend` 기록에서 많이 골라진 것부터 `compiled`로 만듭니다. 산식이 있는 37종과 기한 규칙이 있는 70종은 `computed` 후보로 표시합니다.
- 가이드의 출처가 불분명합니다(architecture.md 허점 16). 가이드 원문을 앱에 싣고 모델에 보내는 것이므로 배포 전에 권리 확인이 필요합니다. 그전에는 개발 빌드에만 싣습니다.

재는 값은 실행마다 모델 요청 수, 입력과 출력 토큰, 요청 본문 바이트, 걸린 초, 도구 호출 수, 채점 결과입니다. 요청 하나가 장부 한 줄(`LedgerEntry`)이고, Rust의 문이 적습니다.

- 이 경로는 요금이 아니라 사용자의 요금제 한도를 씁니다. 그래서 비용은 토큰과 요청 수와 초로 적습니다.
- 응답에 사용량이 담기면 Mastra가 스텝을 합쳐 돌려주는 것은 가짜 서버로 확인했습니다. 실계정 응답에 담기는지는 미확인입니다. 없으면 요청 본문 바이트로 비교합니다.
- `temperature`를 보낼 수 없어 실행마다 결과가 달라집니다. 입력마다 5번 돌리고 평균이 아니라 분포를 적습니다.
- 바닐라의 문답은 사실을 첫 메시지에 다 주는 방식으로 먼저 잽니다. 사용자를 흉내 내는 모델은 그다음입니다.
- 계산은 바닐라가 다 맞혀도 코드에 둡니다. 그 측정은 형태를 고르려는 것이 아니라 틀리는 정도를 숫자로 남기려는 것입니다.
- 형태를 바꾸는 기준은 이렇습니다. 한 단계 더 깎은 판이 통과율에서 앞 판보다 낮으면 그 단위의 지시문과 도구를 다시 봅니다. 통과율이 같고 요청 수와 토큰이 줄지 않으면 그 단위는 앞 판의 형태로 되돌립니다.
- 실계정이 필요한 실행은 개발 기기에서 사람이 돌립니다. CI는 녹화한 스트림을 문 자리에 넣어 다시 돌립니다.

## 9. 첫 조각

**지급명령 신청서 양식에서, 붙여 넣은 글로 답 후보를 채우는 `fill` 턴 하나를 끝까지 만듭니다.** 이미 되는 문서에 눈에 보이는 가치가 붙고, 설계의 위험한 부분인 배선, 강제 도구 호출, 가리기와 승인, 가리키기, 프로세스 경계, 장부를 한 번에 지납니다. 코어의 템플릿 전환(다음 구조 4단계)을 기다리지 않습니다.

1. **배선 확인(앱 없이, 스크립트 하나).** Mastra 에이전트 → `shapeRequest` → 실계정. 가짜 서버로는 요청 모양과 도구 왕복을 이미 확인했습니다(11장). 실계정에서 볼 것은 넷입니다. 최상위 함수 도구를 그대로 받는지, 네임스페이스로 묶어야 하는지. 강제 함수 호출 한 번이 `response.completed`까지 가는지. `developer` 역할 지시문과 `include` 필드를 받는지. 사용량이 오는지. 여기서 막히면 뒤 단계를 시작하지 않습니다.
2. 하네스 프로세스와 `HarnessPort`, `CorePort`. Rust 셸의 `assist_*` 명령, 로그인, 나가는 문(`netFetch`, `egress_check`, 기록).
3. 코어: `Field`에 `sensitivity`, `mask`, `resolve`(금액과 날짜 말 읽기. "700만 원"은 읽고, "3월 말"처럼 날짜가 정해지지 않는 말은 후보로 만들지 않고, 연도가 없는 날짜는 표시를 붙임).
4. 양식 화면의 승인 화면과 후보 표시.
5. 장부, 평가 실행기, 답 뽑기 단위의 바닐라 측정.

**끝내는 검사**는 `scripts/box run 'pnpm harness:eval extract_answers --replay'`가 통과하고, 같은 평가를 실계정으로 한 번 돌린 장부가 붙는 것입니다. 통과 조건은 넷입니다.

- 코어가 읽지 못한 값이 후보가 된 건수 0.
- 기록된 요청 본문 전체에서 픽스처의 개인정보 문자열이 0건. 픽스처의 글과 개인정보 목록은 정규식을 쓴 사람이 아닌 사람이 씁니다.
- 픽스처마다 모델 요청이 1회.
- 바닐라와 깎은 것의 `UnitCost` 표가 나오고, 틀린 값이 받아들여진 수가 바닐라보다 많지 않음.

그다음 순서는 `recommend`, 코어의 `check_prose`와 `compose`(자리 이름만 쓰게 하는 방식이 모델로 처음 시험됨), `research`, 빈칸 서식(`blank`), 가이드 변환 명령줄입니다.

## 10. 아직 만들지 않는 것

| 만들지 않는 것 | 이유 |
| --- | --- |
| 대화 기억(Mastra 메모리, 스레드 저장) | 상태는 앱에 있고 턴마다 입력을 새로 만듭니다. 기억을 쌓으면 스텝마다 다시 보내는 양이 늘고, 나간 글을 따지기 어려워집니다. |
| Mastra 워크플로와 중단, 재개 | 문답은 양식이 합니다. `plan()`은 작은 함수입니다. 턴이 앱 재시작을 넘어 이어져야 할 때 다시 봅니다. |
| 하위 에이전트, 여러 제공자 | 턴이 이미 일을 나눕니다. 제공자는 하나로 정해졌습니다. |
| 편집기 안에서 문단 고쳐 쓰기 | 편집기의 글에는 실제 값이 들어 있습니다. 값을 자리 이름으로 되돌리려면 글 조각이 어느 필드에서 왔는지 알아야 하는데, Univer의 `customRanges`가 아직 확인되지 않았습니다. |
| 개체명 모델로 가리기 | 6장. |
| korean-law-mcp를 기기에서 직접 돌리기 | Node 20.19 이상을 사용자 기기에 요구합니다. |
| 앱 실행 중 수치 표 자동 확인 | 사용자마다 법제처 키가 필요해집니다. 관리자 명령줄과 CI로 충분하고, 화면은 표의 확인일을 보여 줍니다. |
| 모델 글을 화면에 흘려 보여 주기 | 결과가 도구 인자라 검사 전에는 보여 줄 수 없습니다. 진행 단계만 보여 줍니다. |
| 하네스 실행 파일을 따로 내려받게 하기 | 116MB가 문제인지는 macOS와 Windows 크기를 잰 뒤에 정합니다. |

## 11. 근거와 미확인

가짜 서버로 확인한 것입니다. 이 경로의 문서화된 규칙을 검사하는 서버를 박스에 띄우고 Mastra 1.85.0과 `@ai-sdk/openai` 4.0.121이 보내는 요청을 받아 봤습니다. Mastra가 무엇을 보내는지는 확인했지만 OpenAI가 그것을 받는지는 확인하지 못했습니다.

| 확인한 것 | 결과 |
| --- | --- |
| Mastra 모델을 `{ id: "openai/…", url }`이나 `{ id: "custom/…", url }`로 주면 | `/v1/chat/completions`로 보냄. 이 경로에 맞지 않음 |
| AI SDK `createOpenAI(...)("모델")`로 주면 | `/v1/responses`, `stream: true` |
| `store` | 기본으로는 보내지 않음. `providerOptions.openai.store = false`를 줘야 `false`가 감. 그때 `include` 필드가 함께 감 |
| 지시문 | 입력의 `developer` 역할 항목으로 감. `system` 역할은 보내지 않음 |
| 함수 도구 | 최상위 `tools`에 네임스페이스 없이 감. 이름은 `createTool`의 `id`가 아니라 `tools` 객체의 키 |
| 도구 왕복 | 요청 2회, 도구 실행 1회, 최종 글까지 감 |
| 사용량 | 응답에 담기면 Mastra가 스텝을 합쳐 돌려줌 |
| 금지 필드 | 최소 호출에서는 하나도 보내지 않음 |

문서에서 확인한 것입니다(2026-11-20에 읽음).

- Mastra `Agent`: `instructions`, `model`, `tools`는 `requestContext`의 함수일 수 있음. `stream()` 옵션에 `instructions`, `toolChoice`, `activeTools`, `maxSteps`, `prepareStep`, `providerOptions`가 있음.
- Mastra `createTool`: `id`, `description`, `inputSchema`, `outputSchema`, `execute(input, context)`, `toModelOutput`.
- `@mastra/mcp`의 `MCPClient`: `url`을 주면 Streamable HTTP. 요청마다 바뀌는 헤더는 사용자 정의 `fetch`로 줌. `listToolsets()`는 서버 이름 접두사 없이 도구를 줌.
- AI SDK `createOpenAI`: `baseURL`, 요청을 가로채는 `fetch`. 제공자 옵션 `store`, `systemMessageMode`.
- Sign in with ChatGPT 미리보기 제한: `store: false`, `stream: true`. 빼야 할 필드 목록. `role: "system"` 항목은 거부되고 `instructions`나 developer 메시지를 써야 함. 함수 도구는 네임스페이스로 묶거나 `additional_tools` 입력 항목으로 주라고 되어 있음. 호스팅 MCP는 안 됨. 오류 코드와 상태값은 5장에 적은 대로임.

미확인입니다. 번호는 첫 조각의 어느 단계에서 풀리는지입니다.

- 실계정이 최상위 함수 도구를 받는지. 네임스페이스가 필요하면 그 모양과 도구 강제(`tool_choice`)의 모양. (1)
- 실계정이 `developer` 역할 지시문과 `include` 필드를 받는지. (1)
- 실계정 응답에 사용량이 담기는지. 프롬프트 캐시가 적용되는지. (1)
- 여러 스텝 턴에서 종료 도구가 불린 뒤 반복을 멈추는 방법. 첫 조각은 `maxSteps: 1`만 써서 여기에 기대지 않습니다. (`explain`을 만들 때)
- Rust에서 하는 로그인의 클라이언트 등록 세부. (2)
- 표준 입출력으로 스트림 응답을 넘길 때의 지연. (2)
- 하네스 실행 파일의 macOS와 Windows 크기와 시작 시간. (2)
- 모델이 자리 이름만 쓰고 숫자를 쓰지 않는 지시를 얼마나 지키는지. (`compose`를 만들 때)
- 일반 사용자가 법제처 키를 얻는 절차, 공개 서버의 키 없는 한도. (`research`를 만들 때)

## 검토한 대안

| 대안 | 버린 이유 |
| --- | --- |
| 모델이 이끄는 반복 하나. `SKILL.md`를 지시문으로, 도구를 전부 주고 모델이 다음 단계를 정함 | 스킬의 원래 모양이고 가장 빨리 됩니다. 그러나 모델이 계산을 전부 하고, 대화가 쌓일수록 스텝마다 다시 보내는 양이 늘며, 틀린 값을 막을 자리가 없습니다. 버리지 않고 측정의 기준선으로 씁니다. |
| 모델이 값을 쓰고 코드가 뒤에서 검사 | 검토자가 이미 깼습니다. "글 속 숫자가 입력에 있었는지" 검사는 맞는 잔액을 거부하고 뒤바뀐 금액을 통과시켰습니다. 가리키기는 값을 쓰는 칸 자체를 없앱니다. |
| 문답을 모델이 진행(한 번에 질문 2~3개, 스킬의 방식) | 질문과 순서와 분기는 코어의 `Form`에 이미 있습니다. 모델에게 다시 시키면 질문마다 요청이 들고, 양식과 다른 것을 물을 수 있습니다. |
| `text.format` JSON 스키마로 구조화된 결과 받기 | 이 경로에서 되는지 문서에 없습니다. 함수 도구는 문서에 있습니다. 된다고 확인되어도 얻는 것이 적습니다. |
| korean-law-mcp의 도구 10개를 모델에 그대로 주기 | 4장의 네 가지 이유. 특히 실패한 조회 뒤에 기억으로 답하는 것을 출처 이름 없이는 코드로 막을 수 없습니다. |
| 가이드를 매번 모델이 도구로 통째로 읽기 | 가이드는 6~46KB입니다. 읽은 뒤의 모든 스텝이 그 전체를 다시 보냅니다. 코드가 아는 절만 끼웁니다. |
| 찾기 도구로 문서 추천(`guide_find`) | 카탈로그가 7.6KB라 지시문에 들어갑니다. 측정에서 추천 정확도가 낮으면 다시 봅니다. |
| 하네스가 로컬 HTTP 서버를 띄우고 화면이 직접 부름(Mastra 문서가 안내하는 모양) | 포트가 열리고, 화면이 원문을 하네스에 바로 보낼 수 있어 가리기를 건너뛸 길이 생깁니다. |
| 코어를 WASM이나 네이티브 모듈로 하네스에 넣기 | 왕복은 줄지만 코어가 두 벌로 빌드되고, 개인정보가 하네스 프로세스 안으로 들어옵니다. |
| 턴 결정을 Rust나 하네스에 두기 | 화면 상태가 React에 있어 `plan()`은 화면 쪽 TypeScript에 둡니다. 하네스에 두면 하네스가 상태를 갖게 되어 같은 요청을 다시 돌릴 수 없습니다. 받아들이는 검사는 Rust에 있으므로 화면이 틀려도 틀린 값이 통과하지는 않습니다. |
| 턴 종류마다 Mastra 에이전트를 따로 만들기 | 턴마다 달라지는 것은 지시문, 도구, 스텝 수뿐이고 표 하나로 충분합니다. 에이전트를 나누면 위임과 기억 같은 기능을 쓰고 싶어집니다. |
| 149개 문서를 모델이 가이드만 보고 쓰게 하고 "검토받지 않음"을 붙이기 | 약속 1에는 표시로 넘어갈 예외가 없습니다. 가이드 25개는 값이 "자동 계산된다"고 하지만 코드가 없고, 57개는 수치가 낡을 수 있다고 스스로 적습니다. |
| 149개 문서를 카탈로그에서 숨기거나 추천과 설명만 하기 | 추천의 대부분이 "초안 없음"이 됩니다. 빈칸 서식은 코드만으로 지금 됩니다. |
| 하네스가 네트워크에 직접 나가고 토큰을 가짐 | 요청 모양은 지킬 수 있지만, 무엇이 나갔는지를 하네스의 자기 보고로만 알게 됩니다. Rust가 직접 보내면 검사와 기록이 한 곳에 있고 토큰이 JS 프로세스에 생기지 않습니다. 값은 표준 입출력으로 스트림을 넘기는 배관입니다. |
| 턴 종류마다 에이전트를 두고 도구 선택을 모델에 맡긴 채 턴 안에서 고쳐 쓰게 하기 | 스텝마다 입력 전체를 다시 보내는 경로라 스텝 수가 곧 비용입니다. 도구를 강제하고 요청 한 번으로 끝내며, 고쳐 다시 시키기는 턴 밖에서 한 번만 합니다. |
| 모델에게 계산 도구를 주고 피연산자를 넘기게 하기 | 계산은 코드가 하지만 숫자는 모델이 고릅니다. 맞는 금액을 틀린 자리에 넣는 것을 막을 수 없습니다. 값은 사용자가 양식에 넣거나 코어가 원문에서 읽습니다. |
| 149개 문서를 실행 중에 모델이 빈칸을 묶어 조립 | 가이드의 분기는 자연어라 코드가 고를 수 없고, 결국 모델이 분기와 값을 정합니다. 빈칸 서식(`blank`)은 모델 없이 되고 약속 1을 어기지 않습니다. |

## 이 설계가 나온 과정

같은 과제를 세 모델에게 따로 맡겨 세 안을 받았습니다. 세 안이 같은 뼈대로 모였습니다. 턴은 코드가 정하고, 모델은 값을 쓰지 않고 가리키며, 하네스는 표준 입출력으로 Rust와 말하고, 법령 도구는 감싸서 성공한 조회에만 이름을 줍니다.

- **기준안**은 턴마다 요청 한 번으로 끝내고 받아들이는 규칙이 턴 표에 있는 안입니다. 다른 회사 모델인 심판도 같은 안을 골랐습니다(30점 만점에 28, 27, 15).
- **접붙인 것**: 나가는 문을 Rust 하나로 모으기, 149개 문서의 빈칸 서식과 명령줄 변환, 판을 넷으로 나눈 측정과 실패 주입, 서술 턴에 주는 사실의 모양, 오류 분류, 고지를 화면이 맡기.
- **가짜 서버 실험**으로 세 안이 모두 미확인으로 남긴 요청 모양을 확인해 11장에 적었습니다.
