# LDoc 구조와 설계

LDoc은 한국 법률문서를 작성하는 데스크톱 앱입니다. 사용자가 질문에 답하면 앱이 금액과 날짜와 문구를 계산해 초안을 만들고, 사용자는 편집기에서 고친 뒤 제출용 파일로 내보냅니다.

이 문서는 왜 이렇게 설계했는지를 설명합니다. 결정한 것, 아직 결정하지 않은 것, 알려진 허점을 구분해서 적습니다.

## 지켜야 할 것

1. 금액, 날짜, 법정 수치, 조문 인용은 틀리면 안 됩니다. 이 값들은 코드가 계산하고, 언어 모델이 쓰지 않습니다.
2. 당사자의 이름, 주민등록번호, 주소는 사용자가 켜지 않는 한 기기 밖으로 나가지 않습니다.
3. 편집기에서 본 것과 내보낸 파일이 같아야 합니다.
4. 법률 검토를 받지 않은 문서는 검토를 받지 않았다고 화면에 표시합니다.

## 구조

```
React 화면 (src/)
	양식 렌더링, Univer Docs 편집기, 비용과 안내 표시
		│  Tauri IPC. 타입은 src/bindings/ (코어에서 생성)
Tauri 셸 (src-tauri/)
	명령 네 개: catalog, form, draft, export_docx
		│
ldoc-core (crates/ldoc-core/)
	양식 정의, 입력 해석, 수수료와 이율 계산, 문구 생성, DOCX 쓰기
```

- **코어가 사실을 전부 가집니다.** 화면은 돈과 날짜를 계산하지 않습니다. 코어는 셸과 편집기를 모릅니다. 그래서 코어는 `cargo test`만으로 검증됩니다.
- **서버가 없습니다.** 데스크톱 앱이라 axum을 쓰지 않습니다. 화면과 코어는 Tauri IPC로 통신합니다.
- **화면은 양식을 모릅니다.** 화면은 코어가 준 `Form`을 그대로 그립니다. 문서 종류가 늘어도 화면 코드는 늘지 않습니다.
- **`Document`가 유일한 교환 형식입니다.** 코어가 만든 초안, 편집기의 내용, DOCX 작성기가 모두 `Document`를 주고받습니다. 편집기를 바꾸려면 변환 모듈 하나만 다시 쓰면 됩니다.

## 자료 구조

| 타입 | 뜻 | 위치 |
| --- | --- | --- |
| `Form` | 단계, 필드, 선택지, 표시 조건 | `form.rs` |
| `Answers` | 필드 id에서 문자열 또는 문자열 배열로 가는 원본 입력 | `form.rs` |
| `Reader` | `Answers`를 타입 있는 값으로 읽고 오류를 전부 모음 | `form.rs` |
| `Won` | 음수와 소수가 없는 원화 금액 | `money.rs` |
| `Dated<T>` | 시행일이 붙은 수치 표 | `rates.rs` |
| `Document`, `Block` | 문단 목록. 문단은 글, 정렬, 굵기, 크기 | `document.rs` |
| `Draft` | 문서, 비용 내역, 안내 문구 | `docs/mod.rs` |
| `DocKind` | 문서 종류 하나. 양식 함수와 초안 함수의 쌍 | `docs/mod.rs` |

문서 종류는 `KINDS` 표에 등록합니다. 문서 하나는 모듈 하나입니다. 모듈은 `Answers`를 자기 타입(`Request`)으로 한 번 해석하고, 그 뒤의 코드는 해석된 값만 씁니다.

선택지는 `Choices<T>` 표 하나에서 양식과 해석기가 함께 나옵니다. 양식에 보이는 선택지를 해석기가 모르는 일은 생기지 않습니다.

## 결정한 것

### 계산은 Rust 코어에서 합니다

계산량은 작습니다. 가이드 150개 중 37개에 산식이 71줄 있고 전부 사칙연산입니다. Rust를 고른 이유는 속도가 아닙니다. 데스크톱 셸이 Rust이고, 정수 금액과 날짜를 타입으로 묶을 수 있기 때문입니다.

### 편집기는 Univer Docs 오픈소스판입니다

`@univerjs/preset-docs-core`만 씁니다. `@univerjs-pro/*`는 쓰지 않습니다. DOCX 내보내기는 유료 변환 서버가 필요해서 직접 만듭니다(`docx.rs`).

### 언어 모델은 선택 기능이고 서술만 씁니다

기본은 꺼져 있습니다. 켜면 세 곳에 씁니다.

1. 상황 설명에서 문서 종류 추천.
2. 사실관계 문단 초안.
3. 붙여 넣은 계약서나 문자에서 답 후보 추출.

API 키는 OS 키체인에 둡니다. 모델 호출을 어디서 하고 어떤 프레임워크를 쓸지는 [아직 정하지 않았습니다](#모델-호출을-어디에-둘-것인가).

보내기 전에 가리는 방법은 처음 안이 틀렸습니다. 처음 안은 양식에 입력된 값을 문자열 일치로 가리면 탐지 모델이 필요 없다고 했습니다. 검토자 두 명이 시제품으로 깼습니다.

- 붙여 넣은 글은 `(주)가나푸드`, `김 가나`, `서울 서초구`처럼 양식과 다르게 적습니다. 문자열 일치는 이 값을 놓칩니다.
- 문서 추천과 답 추출은 양식을 채우기 전에 일어납니다. 대조할 값이 아직 없습니다.

그래서 약속을 바꿉니다. 앱은 보낼 글을 가린 상태로 먼저 보여 주고, 사용자가 승인한 글만 보냅니다. 가리는 수단은 표기 차이를 흡수한 사전 대조, 정규식, 개체명 모델을 함께 씁니다.

모델이 쓴 글을 받는 규칙은 [다음 구조](#문구는-템플릿-사실은-rust)에 있습니다. 처음 안은 "글 속 숫자가 입력에 있던 숫자인지"를 봤는데, 맞는 잔액을 거부하고 금액이 뒤바뀐 문장을 통과시켰습니다.

### 빌드와 테스트는 instabox 박스에서 합니다

`scripts/box`가 작업 트리를 박스 `ldoc-dev`로 보내고 거기서 실행합니다. 개발 기기에서는 cargo와 pnpm을 돌리지 않습니다.

## 다음 구조

검토에서 나온 허점은 대부분 원인 네 개로 모입니다. 구조는 원인마다 주인을 하나씩 정합니다.

| 원인 | 지금 | 다음 |
| --- | --- | --- |
| 원본 문자열이 경계를 넘어 들어옴 | `String`, 검사 없는 `Won` | `Reader`가 경계 타입으로만 내줌 |
| 문구를 코드가 가짐 | `format!` 241줄 | 템플릿 파일과 `Facts` |
| 법정 수치에 출처가 없음 | `Dated<T>` | 출처와 확인일이 붙은 `Table<T>` |
| 문서 모델이 편집기보다 얇음 | 문단 하나에 서식 하나 | 문단 안에 글 조각 |

### 경계 타입

`Answers`는 `Reader`를 지나야 값이 됩니다. `Reader` 뒤의 코드는 아래 타입만 받습니다.

```rust
/// 한 줄짜리 글. 줄바꿈, 제어 문자, XML에 쓸 수 없는 문자가 없다.
pub struct Line(String);

/// 0원 이상 999조 원 이하. 쉼표는 세 자리 묶음일 때만 읽는다. 공백은 읽지 않는다.
pub struct Won(u64);

/// 무슨 번호인지가 타입에 있다. 문서는 그 이름으로 적는다.
pub enum PartyId {
	Resident(Line),
	Corporate(Line),
	Business(Line),
}

pub enum Problem {
	Missing,
	NotAChoice,
	Malformed(&'static str),
	Conflict(&'static str),
}
```

문서 모듈의 해석은 두 단계입니다. 첫 단계는 필드를 하나씩 읽습니다. 둘째 단계는 필드 사이의 관계를 봅니다. 날짜의 앞뒤, 채권자와 채무자가 같은지, 청구할 잔액이 있는지가 여기에 속합니다. 오류는 원인이 된 필드에 붙입니다.

### 문구는 템플릿, 사실은 Rust

두 안을 비교했습니다.

| | 템플릿 파일과 `Facts` | Rust 문구와 기준 출력 파일 |
| --- | --- | --- |
| 법률가가 읽는 것 | 분기가 보이는 템플릿 | 표본 출력만. 표본에 없는 분기는 검토되지 않음 |
| 문구 수정 | 검토자가 직접 | 개발자가 대신 |
| 가이드에서 옮기기 | 가이드의 출력 템플릿과 같은 모양 | 문장마다 다시 씀 |
| 오타 검출 | 렌더링할 때 | 컴파일할 때 |
| 줄바꿈과 공백 | 규칙을 알아야 함 | 문제 없음 |

템플릿으로 정합니다. 근거는 실험입니다. 지급명령 신청서를 69줄 템플릿과 `Facts`로 다시 쓰고 15개 분기에서 현재 Rust 출력과 비교했습니다. 글과 서식이 모두 같았습니다. Rust 문구 241줄이 템플릿 69줄과 `Facts` 약 110줄로 바뀝니다. 코드는 크게 줄지 않습니다. 얻는 것은 검토 가능성입니다.

```rust
struct DocKind {
	id: &'static str,
	form: fn() -> Form,
	template: &'static str,
	draft: fn(&Answers) -> Result<Draft, Vec<FieldError>>,
	review: Review,
}

enum Review {
	Unreviewed,
	Reviewed { by: &'static str, on: Date },
}

// 문서 모듈마다
fn parse(answers: &Answers) -> Result<Request, Vec<FieldError>>;
fn facts(request: &Request) -> Facts; // 본문에 나올 수 있는 값 전부
fn costs(request: &Request) -> Vec<CostLine>;

// 공통, docs/template.rs
fn render(template: &str, facts: &impl Serialize) -> Result<Document, TemplateError>;
```

템플릿이 지킬 규칙은 네 가지이고, 불러올 때 검사합니다.

1. 템플릿은 `Facts`의 참거짓, 있음과 없음, 종류로만 갈라집니다. 계산과 크기 비교는 `Facts`가 합니다.
2. 없는 값을 쓰면 렌더링이 실패합니다. 실험에서 `{{ balnce }}`는 빈칸이 아니라 오류가 됐습니다.
3. 글이 있는 줄은 `%}`로 끝나지 않습니다. 끝나면 다음 줄과 붙습니다.
4. `Facts`의 글은 전부 `Line`입니다. 실험에서 주소에 줄바꿈을 넣으니 가짜 제목 문단이 만들어졌습니다. `Line`이 이 경로를 막습니다.

언어 모델이 쓴 서술도 같은 형식으로 받습니다. 모델은 숫자를 쓰지 않고 `{{ balance }}` 같은 자리 이름만 씁니다. 받은 글에 자리 밖의 숫자, 한글 수사, 조문 번호, 제어 구문이 있으면 버립니다. 그 뒤에 같은 `render`가 값을 채웁니다.

### 법정 수치 표

```rust
pub struct Table<T: 'static> {
	rows: &'static [(Date, T)],
	source: &'static str,
	verified_on: Date,
}

pub struct Cited<T> {
	pub value: T,
	pub in_force_from: Date,
	pub source: &'static str,
	pub verified_on: Date,
}

impl<T: Copy> Table<T> {
	pub fn on(&self, day: Date) -> Option<Cited<T>>;
}
```

`Draft`는 쓴 수치마다 `Cited`를 함께 돌려줍니다. 화면은 값 옆에 출처와 확인일을 보여 주고, 신청일이 확인일보다 180일 넘게 뒤면 경고합니다.

### 문서 모델

```rust
pub struct Document {
	pub paragraphs: Vec<Paragraph>,
}

pub struct Paragraph {
	pub role: Role,
	pub runs: Vec<Run>,
	pub align: Align,
	pub half_points: u16,
}

pub enum Role {
	Title,
	Heading { section: String },
	Body,
}

pub struct Run {
	pub text: String,
	pub bold: bool,
	pub underline: bool,
}
```

- 구역을 묶은 나무 구조는 쓰지 않습니다. 편집기와 DOCX가 모두 문단의 나열이라서, 구역은 `Heading`에서 다음 `Heading`까지로 읽습니다. 항목별 복사가 이 규칙을 씁니다.
- 크기는 반 포인트 정수입니다. 지금은 편집기가 10.5pt를 주면 `Document`가 읽기를 거부합니다.
- 편집기 도구 모음에는 `Run`이 담는 것만 남깁니다. 지금 화면에는 기울임, 취소선, 첨자, 글자색, 글꼴 선택이 있고 전부 내보낼 때 사라집니다.
- `Role`이 편집을 거쳐도 남는지는 Univer에서 아직 확인하지 않았습니다.

### 셸

```rust

async fn export_docx(app: AppHandle, document: Document) -> Result<Option<String>, ExportError>;
```

저장 대화상자를 Rust가 엽니다. 화면은 경로를 넘기지 않습니다. 돌려주는 값은 저장된 파일 이름이고, 사용자가 취소하면 `None`입니다.

## 아직 결정하지 않은 것

### 모델 호출을 어디에 둘 것인가

여러 AI 제공자를 지원하려고 합니다. 처음 안은 Mastra를 한 줄로 배제했는데 근거가 부족했습니다. 선택지는 셋입니다.

| | Rust에서 직접 호출 | Mastra 사이드카 | Mastra 서버 |
| --- | --- | --- | --- |
| 실행 위치 | 앱 안의 Rust | 앱에 동봉한 실행 파일 | 운영하는 서버 |
| 제공자 추가 | 어댑터를 직접 작성. OpenAI 호환 규격과 Anthropic 두 개로 대부분 닿음 | 문자열 하나(`"provider/model"`). 문서 기준 312개 제공자 | 사이드카와 같음 |
| 도구 호출, 작업 흐름, 평가 | 직접 구현 | 있음 | 있음 |
| 앱 크기 | 13.9MB 그대로 | 약 116MB 추가 | 그대로 |
| API 키 | 사용자 키, Rust가 보관 | 사용자 키, 사이드카에 전달 | 서비스 키, 서버가 보관 |
| 사용자 글의 이동 | 기기에서 제공자로 | 기기에서 제공자로 | 기기에서 우리 서버를 거쳐 제공자로 |

측정한 값입니다. Mastra 1.85.0 에이전트를 Bun으로 단일 실행 파일로 묶으면 116.0MB이고, 그중 104.1MB는 빈 프로그램에도 드는 Bun 런타임입니다. 시작에서 종료까지 383~439ms였습니다(3회). Linux x86_64 한 대에서 쟀고, 모델 호출은 하지 않았습니다. macOS와 Windows 크기는 재지 않았습니다.

Mastra 문서는 브라우저 안에서 에이전트를 돌리는 방법을 안내하지 않습니다. 서버를 띄우고 화면이 그 서버를 부르는 구조만 안내합니다. 그래서 웹뷰에 직접 넣는 안은 없습니다.

정해진 조건은 셋입니다. 사용자가 자기 키나 자기 로그인을 씁니다. T3 Code처럼 로그인 방식도 지원합니다. korean-law-mcp 같은 MCP 도구를 모델이 부릅니다.

이 조건에서는 제공자가 두 종류로 나뉩니다.

| | CLI 하네스 (로그인) | 모델 API (키) |
| --- | --- | --- |
| 예 | Claude Code, Codex CLI, OpenCode | Anthropic, OpenAI, Gemini, 로컬 모델 |
| 인증 | 사용자가 그 CLI에서 직접 로그인 | 사용자가 앱에 키를 붙여 넣음 |
| 도구 호출 반복과 MCP 연결 | CLI가 함 | 앱이 해야 함 |
| 앱이 만드는 것 | CLI마다 실행 어댑터 하나 | 반복 실행기와 MCP 클라이언트. Mastra가 여기에 해당 |
| 사용자가 설치할 것 | 그 CLI | 없음 |

T3 Code는 직접 로그인시키지 않습니다. 기기에 설치되고 로그인된 CLI를 실행합니다. 그 CLI는 API 키도 환경 변수로 받으므로, 하네스 방식 하나로 로그인과 키를 모두 다룰 수 있습니다.

하네스 경로는 실행해서 확인했습니다. 로그인된 `claude`를 다음 조건으로 돌렸습니다. MCP 서버는 korean-law 하나만 연결하고, 내장 도구는 전부 끄고, 결과는 JSON 스키마로 받았습니다.

- 9초에 끝났고 API 키 없이 로그인 인증으로 돌았습니다.
- 모델에 주어진 도구는 korean-law의 10개와 결과 제출용 하나뿐이었습니다.
- 모델이 `search_law`와 `get_law_text`를 불렀고 스키마에 맞는 JSON이 나왔습니다.
- 두 호출은 공개 서버의 공용 한도 초과로 실패했습니다. 조회 성공은 아직 확인하지 못했습니다. 법제처 인증키가 있어야 합니다.
- 도구가 실패했는데도 모델은 시효 기간 칸에 3을 채웠습니다. 기억으로 답한 것입니다. 그래서 도구가 필요한 값은 성공한 도구 결과에서만 받도록 코드가 강제해야 합니다.

제약은 다음과 같습니다.

- Anthropic 문서는 제3자 제품이 claude.ai 로그인을 제공하거나 구독 인증을 대신 다루는 것을 금지합니다. 사용자가 직접 설치하고 로그인한 CLI를 앱이 실행하는 T3 Code 방식은 문서에 규정이 없는데, 프로젝트 소유자가 안전하다고 확인했습니다(2026-11-20). 앱은 로그인 정보를 읽거나 저장하지 않고 CLI를 수정하지 않습니다.
- 대상 사용자는 개발자가 아닙니다. CLI 설치와 터미널 로그인은 진입 장벽입니다.
- korean-law-mcp의 공개 서버를 쓰면 모델이 보낸 검색어가 그 서버를 지납니다. 기기에서 법제처로 직접 조회하는 방식은 Node.js 20.19 이상이 필요합니다.
- CLI 버전이 바뀌면 어댑터가 깨질 수 있습니다. T3 Code 문서에도 버전 호환 경고와 갱신 절차가 따로 있습니다.

제공자는 우선 하나로 정했습니다. OpenAI의 "Sign in with ChatGPT"입니다. Claude CLI를 포함한 다른 제공자는 지금 범위에서 뺍니다(2026-11-20, 프로젝트 소유자 결정).

"Sign in with ChatGPT"는 `codex login`과 다릅니다. 위 표의 두 종류 중 오른쪽, 모델 API에 해당합니다.

- 사용자가 OpenAI 로그인 화면에서 자기 ChatGPT 요금제 사용을 앱에 허락합니다. 권한 이름은 `chatgpt.tokens.use.direct`입니다.
- 앱은 접근 토큰(1시간, 갱신 토큰 30일)을 받아 `POST https://api.openai.com/v1/responses`를 직접 부릅니다.
- 그래서 도구 호출 반복, MCP 연결, 턴 제어는 앱이 가져야 합니다. 이 자리에 Mastra를 씁니다(프로젝트 소유자 결정). 문서 작성 스킬과 법령 조회도 Mastra의 도구 호출로 넣습니다.

OpenAI 문서에서 확인한 제약입니다.

- 요청마다 `store`는 `false`, `stream`은 `true`여야 합니다. `temperature`, `top_p`, `max_output_tokens`는 받지 않고, 역할이 `system`인 입력은 거부됩니다.
- 호스팅 MCP는 지원하지 않습니다. MCP는 앱 쪽 클라이언트로 연결해야 합니다.
- 응답에 토큰 사용량이 담기는지는 문서에 없습니다. 단위 업무 비용을 재려면 실제 응답으로 확인해야 합니다.
- 요금제 사용은 "오픈소스 프로젝트, 로컬에서 도는 개인 프로젝트, 선정된 비공개 앱"에 열려 있습니다. 유료이거나 원격 호스팅 앱은 대기 명단에 신청하라고 되어 있습니다. 대상 요금제는 Plus와 Pro입니다.
- Mastra의 OpenAI 연결이 이 제약을 지키며 도는지는 아직 돌려 보지 않았습니다.

깎는 방법은 다음 순서입니다. 업무를 단위로 자릅니다. 도구 없이 스킬과 가이드만 준 상태에서 단위마다 토큰, 턴 수, 시간, 정답률을 잽니다. 그 수치로 단위마다 형태를 고릅니다. 형태는 모델을 쓰지 않는 코드, 하네스에 넣은 도구 호출, MCP, 명령줄 중 하나입니다. 그다음 턴마다 프롬프트와 허용 도구를 좁힙니다.

법령 조회는 본인 인증키로 성공했습니다. 모델 없이 korean-law MCP 서버(4.15.24)를 직접 불러 법제처 원문을 받았고, 코어의 법정 수치를 대조했습니다.

### 답을 바꾸면 편집한 내용은 어떻게 되는가

지금은 다시 만들면 편집이 사라집니다. 1차 안은 다시 만들기 전에 편집본과 새 초안의 차이를 보여 주고 사용자가 고르게 하는 것입니다. 편집기 안의 글을 필드에 묶는 방식은 Univer의 `customRanges`로 가능한지 확인한 뒤 정합니다.

| 문장부호만 남음 | 4 | 14 |
| 글자나 숫자가 남음 | 10 | 1 |

모델 카드는 한국어를 지원하지 않는다고 하지만, 이름은 31개 중 29개를 전부 가렸습니다. 한국어에서 남은 10개 중 4개는 "주식회사"와 "시"처럼 누구인지 알 수 없는 말입니다. 나머지 6개는 실제 누출입니다. 주민등록번호 앞 세 자리, 성 한 글자, 이름의 끝 글자, 동과 호수, 차량 번호, 우편번호 첫 자리입니다.

판단은 이렇습니다. 이 모델 하나로 가리면 안 됩니다. 번호류는 정규식이 먼저 잡고, 이 모델은 이름과 주소를 잡는 보조 수단으로 쓸 수 있습니다.

이 숫자의 한계는 다음과 같습니다.

- 문장은 평가자가 직접 쓴 60개이고 실행은 한 번입니다. 모델이 결정적이라 실행마다 값은 같습니다.
- 모델이 고정한 버전(torch 2.10.0, transformers 4.57.6)이 아니라 Kaggle 기본 버전(2.11.0, 5.20.2)에서 돌았습니다. 영어 이름 31개를 전부 잡았으므로 실행 자체는 정상으로 봅니다.
- 정규식 비교는 같은 사람이 문장과 패턴을 함께 썼으므로 독립된 증거가 아닙니다.
- 모델 크기는 1.1GB입니다. 데스크톱 앱에 넣는 방법은 정하지 않았습니다.
